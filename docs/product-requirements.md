# AI 需求驱动 API 自动化测试平台——产品需求文档（PRD）

> 产品代号：AI Test Tool  
> 文档状态：初稿  
> 版本：0.1.0  
> 更新日期：2026-08-19  
> 目标版本：MVP

## 1. 产品概述

AI Test Tool 是一个面向 QA、开发和产品人员的 API 自动化测试平台。用户提供业务需求文档、API 接口文档和测试环境配置后，系统自动完成需求拆分、接口匹配、调用依赖识别、测试场景规划、测试数据构造、测试执行、失败诊断和报告生成。

产品重点解决跨接口业务链路测试，而非仅对单个接口进行 Schema 校验或随机 Fuzz。

## 2. 背景与问题

当前 API 自动化测试通常面临以下问题：

1. 测试人员需要人工阅读 PRD 和接口文档，再手工建立对应关系。
2. 多接口场景涉及 ID、Token、状态和业务数据传递，编排成本高。
3. OpenAPI 自动测试工具主要验证协议、Schema 和异常输入，难以验证业务语义。
4. 通用大模型可以生成测试代码，但容易引用不存在的接口、字段和依赖。
5. 自动生成的测试缺少需求追溯、版本管理、清理策略和长期维护能力。
6. 当需求或接口变化时，团队难以判断哪些测试需要更新。

## 3. 产品愿景

让团队能够从业务需求出发，持续生成并维护可信的 API 自动化测试资产，使每条重要需求都有对应的可执行验证链路和清晰证据。

## 4. 产品目标

### 4.1 MVP 目标

- 将需求文档解析为可审核的原子需求和业务规则。
- 将 OpenAPI 转换为可搜索、可执行的 API 操作目录。
- 自动完成需求与 API Operation 的候选映射。
- 自动生成 1～5 步的 API 测试链路。
- 自动处理前序响应向后续请求的数据绑定。
- 生成并执行合约断言、通用断言和需求断言。
- 对失败结果进行分类，并对测试自身问题进行有限自动修复。
- 输出需求覆盖矩阵和可复现执行证据。
- 将审核通过的场景导出为 pytest。

### 4.2 成功指标

| 指标 | MVP 目标 |
|---|---:|
| OpenAPI 解析成功率 | ≥ 95%（针对合规 OpenAPI 3.0/3.1） |
| 需求原子化人工接受率 | ≥ 80% |
| 需求—接口映射 Top-3 命中率 | ≥ 85% |
| Test IR Schema 首次有效率 | ≥ 90% |
| 候选场景经不超过两次修复后的可执行率 | ≥ 75% |
| 业务断言人工接受率 | ≥ 70% |
| 生成场景假阳性率 | ≤ 15% |
| 测试结果需求可追溯率 | 100% |

指标需要通过内部 Golden Set 和至少三个真实试点项目共同评估。

## 5. 用户角色

### 5.1 QA / 测试工程师

主要目标：减少测试设计和脚本编写工作，审查自动生成场景，执行回归测试并定位缺陷。

### 5.2 开发工程师

主要目标：验证 API 实现、补充接口示例、在 CI 中执行测试并快速复现问题。

### 5.3 产品经理 / 业务分析师

主要目标：确认业务需求是否被测试覆盖，审查从需求中提取的业务规则。

### 5.4 项目管理员

主要目标：配置环境、认证、模型、权限、安全策略和数据保留策略。

## 6. 典型用户故事

### US-001：从文档创建测试项目

作为 QA，我希望上传 PRD 和 OpenAPI，让系统自动识别可测试需求和接口，以便快速开始测试设计。

### US-002：生成业务测试链路

作为 QA，我希望系统把“创建商品—下单—查询库存”生成一条可执行链路，并自动传递商品 ID 和订单 ID。

### US-003：审查业务断言

作为产品经理，我希望看到“库存减少 2”这一断言来自需求的具体段落，以便确认系统没有误解业务规则。

### US-004：自动执行和清理

作为开发工程师，我希望测试完成后自动删除创建的订单和商品，避免污染共享测试环境。

### US-005：诊断失败原因

作为 QA，我希望系统区分接口缺陷、接口文档缺陷、测试生成错误和环境故障，而不是只显示断言失败。

### US-006：需求变更影响分析

作为 QA，我希望上传新版需求或 OpenAPI 后，系统列出受影响测试，避免全量重写。

### US-007：导出回归测试

作为开发工程师，我希望把审核通过的场景导出为 pytest 并提交代码仓库，在 CI 中独立运行。

## 7. 核心使用流程

1. 创建项目。
2. 上传需求文档和 OpenAPI。
3. 配置测试环境、认证方式和安全策略。
4. 系统解析文档并展示质量问题。
5. 用户确认原子需求和业务规则。
6. 系统生成需求—接口映射及 API 依赖图。
7. 用户选择需求并生成候选测试场景。
8. 用户审核接口步骤、数据绑定、断言和清理步骤。
9. 系统在测试环境执行场景。
10. 系统分类失败，并对测试缺陷进行受控修复。
11. 用户查看报告、覆盖矩阵和复现信息。
12. 用户批准场景并导出为回归测试资产。

## 8. 功能需求

需求优先级：P0 为 MVP 必须，P1 为 MVP 可选或 V1 优先，P2 为后续规划。

### 8.1 项目管理

#### FR-PROJ-001 创建和管理项目（P0）

系统应支持创建、编辑、归档项目。项目至少包含名称、描述、默认环境、默认模型配置和安全策略。

验收标准：

- 用户可以创建项目并获得唯一项目 ID。
- 项目之间的文档、场景、凭据和运行结果相互隔离。
- 归档项目不可发起新的生成和执行任务，但历史数据仍可查看。

#### FR-PROJ-002 项目成员和角色（P1）

系统应支持管理员、编辑者、审核者和只读用户四种角色。

### 8.2 文档接入

#### FR-DOC-001 上传需求文档（P0）

系统应支持 Markdown、TXT、DOCX；文本型 PDF 为可选支持。

验收标准：

- 单文件大小上限可配置，默认 20 MB。
- 上传后显示文件类型、版本、校验和、解析状态和错误信息。
- 系统保留段落、标题、表格及来源位置，以支持引用追溯。

#### FR-DOC-002 导入 OpenAPI（P0）

系统应支持上传 JSON/YAML 或通过 URL 导入 OpenAPI 3.0/3.1。

验收标准：

- 对不合规规范显示可定位的解析错误。
- 规范导入后展示 Operation、Schema、认证方式、服务器和引用统计。
- 对缺少 operationId、示例、响应 Schema 的接口给出就绪度警告。

#### FR-DOC-003 版本管理（P0）

同一文档的新版本不得覆盖历史版本，系统应保存版本关系和结构化 Diff。

#### FR-DOC-004 Postman/cURL 导入（P1）

系统应支持使用 Postman Collection 或 cURL 补充 API 示例和有效测试数据。

### 8.3 需求解析

#### FR-REQ-001 原子需求提取（P0）

系统应从文档中提取：

- 需求 ID 或生成的内部 ID；
- 角色和业务目标；
- 前置条件；
- 触发动作；
- 输入和具体示例；
- 业务规则；
- 预期结果；
- 异常和边界行为；
- 来源位置和置信度。

#### FR-REQ-002 需求审核（P0）

用户应能确认、编辑、拆分、合并和忽略结构化需求。

验收标准：

- 所有人工修改保留审计记录。
- 未审核需求可生成草稿场景，但不得成为质量门禁用例。

#### FR-REQ-003 歧义和缺失信息识别（P0）

系统应识别以下情况：

- 预期结果不明确；
- 没有具体测试数据或前置状态；
- 同一规则在文档中冲突；
- 需求涉及接口规范中不存在的能力；
- 无法判定调用顺序。

系统不得自行补写关键业务规则，应生成待确认问题。

### 8.4 API 分析与依赖图

#### FR-API-001 API 操作目录（P0）

系统应展示每个 API 的方法、路径、operationId、Tag、请求字段、响应、认证和风险等级。

#### FR-API-002 依赖关系推断（P0）

系统应推断前序响应字段如何绑定到后续请求参数，例如：

```text
createUser.response.id → createOrder.request.userId
```

每条依赖必须提供来源、置信度和映射表达式。

#### FR-API-003 人工编辑依赖（P0）

用户应能新增、修改、禁用和确认依赖边。

#### FR-API-004 运行反馈优化（P1）

系统可根据成功运行结果提高依赖置信度，但不得无审核覆盖用户确认的依赖。

### 8.5 需求—接口映射

#### FR-MAP-001 自动候选映射（P0）

系统应为每条需求推荐相关 API Operation，并说明匹配原因。

验收标准：

- 映射结果只允许引用当前 ApiSpec 中存在的 Operation。
- 默认展示 Top-3 候选及置信度。
- 用户可以确认、替换和补充 Operation。

#### FR-MAP-002 未覆盖能力识别（P0）

当需求无法映射到任何 Operation 时，系统应标记为“接口能力缺失”或“文档信息不足”，而不是生成虚构接口。

### 8.6 测试场景生成

#### FR-SCN-001 生成候选测试场景（P0）

用户选择一个或多个需求后，系统应生成候选场景，至少包含：

- 场景名称和目的；
- 关联需求；
- 前置条件；
- API 步骤和调用顺序；
- 输入数据和变量绑定；
- 响应字段提取；
- 断言；
- 清理步骤；
- 风险等级和置信度。

#### FR-SCN-002 测试类型（P0）

系统应支持：

- 正向流程；
- 必填缺失、类型错误和非法枚举；
- 数值、字符串、日期和集合边界；
- 创建后查询、更新后查询、删除后不可访问；
- 跨接口字段一致性；
- 基础权限缺失和角色错误。

#### FR-SCN-003 场景编辑器（P0）

用户应能以表单/流程视图编辑 Test IR，至少支持调整步骤、参数、变量提取、断言和清理动作。

MVP 可以同时提供 YAML 高级编辑视图。

#### FR-SCN-004 场景静态校验（P0）

保存或执行前必须校验：

- Operation 引用；
- 请求 Schema；
- 变量定义和使用顺序；
- JSONPath/表达式语法；
- Secret 引用；
- 写操作清理策略；
- 最大步骤数和安全策略。

#### FR-SCN-005 批量生成（P1）

用户可按需求模块批量生成场景，并设置每条需求的场景数量上限。

### 8.7 测试数据

#### FR-DATA-001 数据源优先级（P0）

系统应优先使用用户数据和文档示例，其次使用 OpenAPI 示例和约束生成数据，最后才使用模型生成候选数据。

#### FR-DATA-002 动态变量（P0）

系统应支持运行 ID、UUID、时间戳、随机字符串、前序响应字段和环境变量。

#### FR-DATA-003 敏感数据保护（P0）

Secret 不得写入 Test IR 明文、模型 Prompt、报告和导出代码，只能以引用形式存在。

#### FR-DATA-004 数据池（P1）

系统应支持可复用的测试账号、租户、商品和其他业务数据池。

### 8.8 断言与测试 Oracle

#### FR-AST-001 合约断言（P0）

系统应自动生成状态码、Content-Type、响应 Schema 和必需 Header 断言。

#### FR-AST-002 需求断言（P0）

系统应从需求生成业务断言，并展示引用段落、解释和置信度。

#### FR-AST-003 跨步骤断言（P0）

系统应支持比较前后步骤的值，如库存变化、状态迁移、金额计算和创建后读取一致性。

#### FR-AST-004 断言保护（P0）

自动修复不得静默删除、禁用或放宽来源为 `requirement` 或 `user` 的断言。

### 8.9 环境与认证

#### FR-ENV-001 环境管理（P0）

系统应支持 local、dev、test、staging、production 环境及 Base URL、普通变量和 Secret 配置。

#### FR-ENV-002 认证配置（P0）

MVP 支持 API Key、Bearer Token 和静态 Header。用户可以配置登录 API，从响应中提取 Token。

#### FR-ENV-003 生产保护（P0）

production 环境默认禁止自动生成测试和写操作；管理员显式开启后仍需逐次审批。

#### FR-ENV-004 自定义认证脚本（P1）

支持在隔离沙箱运行用户认证 Hook。

### 8.10 测试执行

#### FR-RUN-001 执行单个或批量场景（P0）

用户应能选择环境执行单个场景或场景集合。

#### FR-RUN-002 执行控制（P0）

支持：

- 步骤超时和场景超时；
- 最大并发；
- 请求速率限制；
- 可配置重试；
- 用户取消；
- 写操作全局熔断。

#### FR-RUN-003 数据传递（P0）

执行器应按照 Test IR 将前序响应提取到场景上下文，并在后续请求中解析变量。

#### FR-RUN-004 清理（P0）

无论场景成功、失败或被取消，系统均应尝试执行 finally cleanup。

验收标准：

- 清理动作单独记录结果。
- 清理失败必须显示高优先级告警和待处理资源 ID。

#### FR-RUN-005 可复现信息（P0）

每个失败步骤应提供脱敏后的请求、响应、环境、变量快照、场景版本和可选 cURL。

### 8.11 失败诊断和自动修复

#### FR-DIAG-001 失败分类（P0）

系统应将失败分为 API 缺陷、接口规范缺陷、测试缺陷、环境问题、疑似不稳定和未知。

#### FR-DIAG-002 诊断解释（P0）

系统应说明分类依据、关联需求、失败步骤、预期值、实际值及建议动作。

#### FR-DIAG-003 受控自动修复（P0）

仅当失败被分类为测试缺陷时，系统才可自动修改 Test IR，并且：

- 默认最多两轮；
- 每轮显示修改 Diff；
- 不得放宽需求断言；
- 修复后必须重新经过静态校验；
- 原版本和失败证据不可删除。

#### FR-DIAG-004 不稳定性检测（P1）

系统可重跑失败场景并计算稳定性，区分固定失败和间歇失败。

### 8.12 报告与覆盖率

#### FR-RPT-001 执行报告（P0）

报告至少包含：

- 总体通过/失败/跳过数量；
- 场景和步骤结果；
- 请求响应证据；
- 失败分类和建议；
- 清理结果；
- 执行环境及全部版本信息。

#### FR-RPT-002 需求覆盖矩阵（P0）

矩阵应展示：

```text
需求 → 场景 → API Operation → 断言 → 最近执行结果
```

需求覆盖状态至少包括未分析、未覆盖、草稿覆盖、已审核覆盖、执行通过和执行失败。

#### FR-RPT-003 API 覆盖率（P0）

系统应统计 Operation、方法/路径、状态码和参数覆盖率。不得将这些指标与代码覆盖率混为一谈。

#### FR-RPT-004 报告导出（P1）

支持 JUnit XML、HTML 和 Allure 兼容输出。

### 8.13 测试资产导出

#### FR-EXP-001 pytest 导出（P0）

系统应将已审核 Test IR 导出为可独立运行的 pytest 项目。

验收标准：

- 导出包包含依赖、配置模板、测试代码和 README。
- Secret 使用环境变量占位符。
- 导出测试保留需求 ID 和场景 ID。
- 同一 Test IR 版本重复导出结果应保持稳定。

#### FR-EXP-002 Postman/Jest 导出（P1）

系统应支持 Postman Collection 和 Jest/Supertest 导出器。

### 8.14 变更影响分析

#### FR-DIFF-001 API 变更影响（P1）

新 OpenAPI 版本导入后，系统应识别新增、删除和变更的 Operation、字段及响应，并列出受影响场景。

#### FR-DIFF-002 需求变更影响（P1）

系统应识别需求规则和验收结果的变化，并要求重新审核相关业务断言。

### 8.15 集成

#### FR-INT-001 CI/CD（P1）

提供 CLI 或 API 触发测试，根据通过率、需求覆盖率和严重缺陷设置质量门禁。

#### FR-INT-002 缺陷系统（P2）

支持将已确认缺陷创建到 GitHub Issues、Jira、Linear 等系统。

#### FR-INT-003 Webhook（P1）

测试完成、质量门禁失败和清理失败时可发送 Webhook。

## 9. 页面与信息架构

### 9.1 项目总览

- 文档状态。
- 需求覆盖率。
- API 覆盖率。
- 最近测试运行。
- 待审核项目。
- 高优先级缺陷和清理告警。

### 9.2 文档中心

- 需求文档列表和版本 Diff。
- API 规范列表、解析问题和测试就绪度评分。
- 原始文档与结构化结果对照。

### 9.3 需求中心

- 原子需求列表。
- 业务规则、来源和置信度。
- 歧义问题及确认状态。
- 关联接口和场景。

### 9.4 API 图谱

- API Operation 列表。
- Producer—Consumer 依赖图。
- 字段绑定和置信度。
- 人工确认/禁用操作。

### 9.5 场景编辑器

- 流程/DAG 视图。
- 步骤配置。
- 输入、变量和提取规则。
- 断言及来源。
- 清理计划。
- YAML Test IR 高级模式。

### 9.6 执行与报告

- 实时步骤状态。
- 请求响应和变量快照。
- 失败诊断。
- 自动修复 Diff。
- 覆盖矩阵和导出入口。

## 10. 权限模型

| 操作 | 管理员 | 编辑者 | 审核者 | 只读 |
|---|---:|---:|---:|---:|
| 管理项目和成员 | ✅ | ❌ | ❌ | ❌ |
| 配置环境和 Secret | ✅ | 可选 | ❌ | ❌ |

## 11. 安全与合规需求

### SEC-001 Secret 保护（P0）

Secret 必须加密存储、按项目隔离、按需注入，并在日志、模型上下文和报告中脱敏。

### SEC-002 网络目标控制（P0）

管理员应能配置域名、IP 和端口 Allowlist。系统应拦截环回地址、云元数据地址及未授权内网目标。

### SEC-003 执行隔离（P0）

每个测试任务应在资源受限的隔离 Worker/容器中执行。

### SEC-004 审计日志（P0）

上传、解析、模型生成、人工修改、审批、执行、导出和 Secret 使用均应记录审计事件。

### SEC-005 数据保留（P1）

管理员可配置原始请求响应、模型输入输出和测试报告的保留周期。

## 12. 非功能需求

### NFR-001 可用性

MVP 核心服务月可用性目标为 99.5%。

### NFR-002 性能

- 100 个 Operation 的规范解析 P95 小于 30 秒，不含模型调用。
- 单条需求的候选场景生成 P95 小于 180 秒。
- 运行详情页更新延迟不超过 3 秒。

### NFR-003 可扩展性

文档解析器、模型提供商、认证方式、测试数据生成器和导出器应支持插件式扩展。

### NFR-004 可审计性

任一测试结果必须能够定位到需求版本、接口版本、场景版本、环境版本、模型和提示模板版本。

### NFR-005 可恢复性

生成或执行 Worker 异常退出后，任务状态不得永久停留在运行中；系统应支持安全重试或标记失败。

### NFR-006 国际化

需求解析至少支持中文和英文；同一项目允许混合语言文档。

## 13. MVP 验收场景

### AC-001 CRUD 生命周期

给定包含用户 CRUD 的 OpenAPI 和“管理员可以创建、修改并删除用户”的需求：

- 系统生成创建—查询—更新—查询—删除—删除后查询链路；
- 自动传递 userId；
- 包含状态码、Schema、字段一致性和删除后不可访问断言；
- 无论执行是否成功均尝试清理用户数据。

### AC-002 跨接口业务规则

给定商品、库存和订单 API，以及“购买两件商品后可用库存减少两件”的需求：

- 系统能映射至少三个相关 Operation；
- 生成订单前后库存比较断言；
- 断言可追溯到需求原文；
- 测试失败时不得自动修改“减少两件”这一业务规则。

### AC-003 不完整文档

给定只描述成功响应、没有认证方式的 OpenAPI：

- 系统标记认证和错误响应信息缺失；
- 系统允许生成草稿，但执行前要求补充认证配置；
- 系统不得虚构登录接口。

### AC-004 失败分类

分别模拟返回 500、响应 Schema 不一致、Token 过期和变量绑定错误：

- 系统分别归类为 API 缺陷、规范缺陷、环境问题和测试缺陷；
- 只有变量绑定错误进入自动修复流程。

### AC-005 安全保护

- 未授权目标域名的执行请求被拦截。
- 报告和模型记录中不出现明文 Token。
- 无清理计划的 DELETE/批量写入场景进入高风险审核。

### AC-006 pytest 导出

- 已审核场景可导出并在干净环境安装依赖后运行。
- 测试文件包含需求和场景 ID。
- 导出包不包含明文 Secret。

## 16. 依赖与前置条件

1. 需要至少三套具有真实需求、OpenAPI 和测试环境的试点项目。
2. 需要 QA 和业务人员共同标注 Golden Set。
3. 需要确定首批模型提供商及私有化模型方案。
4. 需要统一 Test IR Schema，并在开发前完成评审。
5. 需要定义可测试环境、数据清理和生产保护政策。

## 17. 主要风险

| 风险 | 产品影响 | 应对措施 |
|---|---|---|
| 需求描述不具备可测试性 | 无法生成可靠业务断言 | 歧义问题、人工确认、需求质量评分 |
| API 文档缺少示例或响应 | 请求成功率低 | 就绪度检查、示例导入、运行反馈 |
| 自动测试污染共享环境 | 阻碍试点采用 | 清理策略、命名空间、风险审批 |
| 用户将生成结果视为绝对正确 | 误报或漏报 | 显示来源、置信度和审核状态 |
| 模型成本随规范规模增长 | 使用成本不可控 | Operation 级检索、缓存和本地模型 |
| 自动修复放宽断言 | 掩盖真实缺陷 | 断言保护、Diff、修复权限边界 |

## 19. 术语表

| 术语 | 定义 |
|---|---|
| Test IR | 独立于具体测试框架的结构化测试中间表示 |
| Oracle | 判断测试结果正确与否的规则或断言 |
| Operation | OpenAPI 中由 method + path 定义的 API 操作 |
| Dependency Edge | 前序 API 输出到后续 API 输入的数据或状态依赖 |
| Requirement Coverage | 已被有效测试场景和断言覆盖的需求比例 |
| API Coverage | Operation、参数和状态码等接口维度的覆盖程度 |
| Golden Set | 由人工确认的需求、映射、场景和断言评测集合 |
| Test Defect | 测试设计或生成错误，而非被测系统错误 |
